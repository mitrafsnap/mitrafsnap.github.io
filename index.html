Container images for evolving ML artifacts

MitraFSnap

Refreshing mounted container data without replacing the container.

An ML service ships a stable runtime together with models, configurations and assets that change all the time. The image pipeline turns every such change into a new image and every new image into a new container, so an update pulls the image, stops the old container, starts a new one and reads the working set again. MitraFSnap updates only the data that changed behind the mount of the running container and keeps the rest in its caches.

Watch the demo Code

Docker, eStargz, 2DFS and MitraFSnap roll out a new detector to the same camera, shown at real speed. The first three restart their containers and their cameras go dark for several seconds. MitraFSnap updates the running container, and its camera keeps running.

The cost of replacing a container

Replacing the container repeats the pull, discards the mounted filesystem and forces the new instance to fetch its working set again, regardless of how little changed. Lazy loading formats shorten the start, but a new version still arrives as a new snapshot with an empty cache. Applying 100 configuration updates to a Gemma 4 31B image by container replacement transfers 4.7 to 5.7 TB, whereas updating the existing mount transfers 87.2 KB.

The information needed to avoid this cost already exists in the image pipeline. Independently built image components record which parts changed between two versions, and the chunk index used for lazy loading records which cached bytes are still valid. MitraFSnap preserves both from the build to the running container.

How it works

1

Builder

The builder packages each model or asset as an independently built and cached allotment and generates its chunk index during the build. An update rebuilds only the allotments it touches.

2

Registry

The registry turns the partition a client selects into a prefetch policy over the complete image. Workers start with different working sets from the same image and can still read every other component on demand.

3

Snapshotter

The snapshotter refreshes a running container. It compares chunk indexes, swaps the readers of the changed layers and invalidates only the changed cached ranges. The application decides when to reopen the new data.

The images remain valid OCI images that standard clients can pull, and the snapshotter is a containerd plugin.

Results

We evaluated MitraFSnap with three language models of up to 59 GB and a video analytics bundle of four models.

8.3–85.9× faster updates in the cloud than container replacement, measured until the application reads the updated files
7.0–265.6× faster updates at the edge
87.2 KB transferred for 100 configuration updates of Gemma 4 31B, compared with 4.7 to 5.7 TB for replacement
6.5× faster rebuild than Docker for an update of 25% of Qwen3.5 9B

Build times stay close to those of 2DFS, and pull times are comparable to those of eStargz.
