Container images for evolving ML artifacts

MitraFSnap

Refreshing mounted container data without replacing the container.

When a model, a configuration or an asset inside an image changes, today's image pipeline replaces the container that uses it: pull the new image, stop the old container, start a new one and read the working set again. MitraFSnap keeps the container running. It updates only the data that changed behind the container's existing mount, and keeps everything else in its caches.

The cost of replacing a container

ML services ship a stable runtime together with models, configurations and assets that change all the time. Every change becomes a new image, and every new image becomes a new container: an update repeats the pull, discards the mounted filesystem and forces the new instance to fetch its working set again, no matter how little actually changed. Lazy-loading formats shorten the start, but a new version still arrives as a new snapshot with an empty cache.

The information needed to avoid this already exists in the image pipeline. Independently built image components identify what changed between versions, and the chunk index used for lazy loading identifies which cached bytes are still valid. MitraFSnap preserves both from construction to the running container.

How it works

1

Builder

Packages each model or asset as an independently built, cached and lazy-loadable allotment, and generates its chunk index during the build. An update rebuilds only the allotments it touches, in parallel.

2

Registry

Turns a client's partition selection into a prefetch policy over the complete image. Workers start with different working sets from the same image, and everything outside the selection stays readable on demand.

3

Snapshotter

Refreshes a running container in place: it compares chunk indexes, swaps the readers of changed layers and invalidates only the changed cached ranges. The application decides when to reopen the new data.

All three are OCI-compatible: images stay valid OCI images that standard clients can pull, and the snapshotter plugs into containerd.

Results

Across three language models of up to 59 GB and a four-model video analytics bundle:

8.3–85.9× faster updates in the cloud than container replacement, measured until the application rereads the updated files
7.0–265.6× faster updates at the edge
87.2 KB transferred for 100 configuration updates of Gemma 4 31B, where replacement transfers 4.7 to 5.7 TB
6.5× faster rebuild than Docker for a 25% update of Qwen3.5 9B

Build performance stays close to 2DFS and pull performance comparable to eStargz.
